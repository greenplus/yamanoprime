# 答え合わせの待ち時間調査 — 2026-10-02

## 結論

4枚出しコレクターはブラウザで判定し、サーバーへの保存を待たずに正誤を表示します。YamanoPrimeは回答POSTで判定・保存した後、SessionのGETまで待って表示します。体感速度の差を説明する大きな違いは、この通信待ちです。

4枚の素数問題では、YamanoPrimeの常駐Pythonワーカーもローカル計測で中央値0.133msでした。Pythonによる素数判定だけを遅さの主因とは判断できません。本番の回答POST内部の計測は行っていないため、実Postgresの処理時間・待ち行列・利用者の回線の寄与は未確定です。

## 実装の比較

| 項目 | 4枚出しコレクター | YamanoPrime |
| --- | --- | --- |
| 判定 | `lib/primes.mjs` の `evaluateConstruction` / `isPrime` をブラウザで実行 | 既存ルールを使うサーバーのPythonワーカーで検証 |
| 正誤表示 | `src/main.mjs` の `answer` でローカル判定直後に表示 | `sendPending` が回答POST、続いて `loadPlay` のGETを待つ |
| ログイン時の保存 | 端末のキューに記録し `void flushAnswers()` で非同期送信。サーバーでも札と素数性を検証 | 回答・得点・統計・反証をトランザクションで確定してから応答 |
| ゲスト時の保存 | ブラウザ保存のみで回答APIへの通信なし | 匿名セッションもサーバー保存 |
| 判定の対象 | A〜Kの4枚による素数構成 | 可変枚数、合成数と材料札、57、1729、詰み申告と反証 |

YamanoPrimeの通常回答POSTは、匿名の場合8 SQL文、最初の回答はプレイ数更新を含め9 SQL文です。その後のSession GETが4 SQL文を実行します。トランザクション開始・終了はこの数に含めません。ログイン時はさらに各HTTPリクエストで共通アカウントを確認します。

ブラウザからの回答はJSONと独自ヘッダーを使うため、CORSの事前確認（OPTIONS）も発生し得ます。現行APIは `Access-Control-Max-Age` を指定していません。実際のOPTIONS回数はブラウザのキャッシュ状況に依存します。

Pythonワーカーは常駐します。本番起動時にも判定を1回実行するため、毎回答でPythonを起動する構造ではありません。

## 計測

Windows / Node 24.19.0。4枚出し937組の同じ合法例を使用。ローカルHTTPの書き込みはPGliteメモリDBのみ。本番にはGET・OPTIONSだけを送信しました。

| 計測対象 | 件数 | 中央値 |
| --- | ---: | ---: |
| コレクターのローカル判定関数 | 1,874 | 0.0014ms |
| YamanoPrimeの常駐ワーカー呼び出し（IPC込み） | 937 | 0.133ms |
| ローカル回答POST（判定・保存込み） | 20 | 19.0ms |
| ローカルの回答後GET | 20 | 13.9ms |
| 上記POST＋GET | 20 | 33.1ms |
| YamanoPrime本番ヘルスチェック | 5 | 198.5ms |
| YamanoPrime本番一覧GET | 5 | 167.5ms |
| コレクター本番ヘルスチェック | 5 | 202.5ms |
| YamanoPrime本番OPTIONS | 5 | 131.6ms |

本番の数値はこの端末からの少数の通信サンプルです。回答POSTの実時間やサービス全体の性能を表すものではありません。両サービスのヘルスチェックは同程度の時間で、コレクターの即時表示はサーバーが桁違いに速いことを意味しません。

生データは [answer-latency.json](answer-latency.json)。再実行：

```powershell
node scripts/measure-answer-latency.mjs 'C:/Users/takum/Documents/game_projects/4枚出しコレクター' --network
```

## 改善する場合の順序

1. 回答POSTはすでに `correct`・`score`・Session集計を返しています。この応答から画面を更新すれば、サーバーでの確定を維持したまま、正誤表示までに待つ追加GETを省けます。
2. CORSの事前確認を適切な期間キャッシュし、不要なOPTIONSを減らします。
3. 問題移動では取得済みの同じ50問を再利用し、ページ変更や復元時に取得します。

コレクターと同じブラウザ判定を導入する場合は、既存ルールの再利用と、合成数・特殊手・大整数・詰みの得点・未同期回答の扱いを合わせる必要があります。まずは1の通信削減が小さな変更で取り組める改善です。

今回の速度に関する作業は調査までです。判定・保存・正誤表示の方式は変更していません。
